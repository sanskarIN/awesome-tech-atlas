**Awesome Tech Atlas** goes beyond a link directory. Every listed resource has a reason to be here: an official starting point, an explanation of when it helps, a practical first step, and honest limitations. We curate **useful, maintainable knowledge**, not the largest possible list.

## What makes an entry useful?

An entry identifies the official source, tells you **what it does and who it is for**, provides a realistic starting action, notes a strength and a limitation, and links to relevant alternatives. The catalog records when the official page was last inspected; that date **does not** claim the entire project was security-audited or its latest release independently tested.

### Editorial principles

1. **Official sources first.** Prefer upstream documentation and maintainers over derivative blog posts.
2. **Accuracy over volume.** No bulk scraping, paid placement, arbitrary rankings, or filler.
3. **Teach the choice.** Explain when to use a resource and when not to.
4. **Keep evidence honest.** Separate documented capabilities from editorial judgments and unknowns.
5. **Respect people and licenses.** Original summaries only; upstream code, text, and trademarks retain their own terms.
6. **Keep contributions approachable.** Markdown and a small, dependency-free Python validator are sufficient.

See the [editorial policy](docs/EDITORIAL_POLICY.md) for verification standards and the [resource template](docs/RESOURCE_TEMPLATE.md) for submissions.

Core areas include programming languages, CS fundamentals, machine learning, deep learning, software engineering, systems and compiler development, operating systems, storage, developer tooling, web/mobile/desktop development, scientific computing, algorithms, architecture, networking, security, cloud/DevOps, and open-source communities. See the [category index](categories/README.md).

## Suggest a correction or resource

Read [CONTRIBUTING.md](CONTRIBUTING.md) and use a [GitHub issue](https://github.com/sanskarIN/awesome-tech-atlas/issues/new/choose) if the change needs discussion. Small evidence-backed fixes can go straight to a pull request. Contributions are reviewed for technical accuracy and usefulness, never accepted automatically.
